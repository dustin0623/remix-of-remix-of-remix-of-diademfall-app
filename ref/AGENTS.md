## Architecture
- Portrait users can browse every page; LandscapeGuard is an in-board mine notice rather than a root modal, and the simulation retains its portrait pause. GameHeader groups Play/House under Play and Heroes/Shop/Fusion under Heroes, alongside Market and Leaderboard. The four controls use a compact dock through 1100px (a header row on wide, short landscape screens); shared Radix dropdowns support mouse hover, click, touch and keyboard, keep the parent category active and mark the current child. Play and House board sizing uses the actual content viewport. Why: rotation must not block navigation, and neither board nor its labeled actions may extend behind fixed controls.
- Account, audio settings and Xaman sign-in share account-windows.css, loaded by the root shell so the homepage and game use the same dialogs. AccountMenuModal receives player identity explicitly, and Test UI opens the real SettingsModal. Overall volume/mute apply to Phaser's sound manager; bomb volume remains the effects channel, with device-local preferences and a matching test sound. Decorative homepage boards always remain silent.
- GameHeader owns navigation, the separate gold/wallet control and the circular player identity; GameHud places it in a dedicated row above the page world. Phones and tablets put identity on the left and gold on the right with a flexible gap and no brand emblem, including wide tablets with a coarse pointer. Category menus use hover/click/tap without chevrons. Header styling lives in game-header.css, with dimmed navigation artwork behind labels that brightens and scales on hover/focus. Why: live routes and Test UI share the same header without overlaying or scrolling page content.
- HudIcon reads the transparent navigation-emblems-atlas.png as a 4-column, 2-row grid: Heroes, House, Play, Fusion, Market, Leaderboard, Shop, brand bomb. Keep these indices stable for shared page headings and give Shop its own cell. Why: one compact emblem set serves navigation and content without duplicate icons or sprite bleed.
- The HUD shell owns one continuous valley backdrop and its 70% dark overlay; the header and compact bottom navigation use warm translucent gradients. Keep the board, controls and decorative ledge above that overlay. Why: navigation matches the wooden game palette while scenery dims independently of interactive content.
- HeroesDrawer is a full-viewport transparent collection overlay with stationary Sort by/Hero selectors and Close control. Its one gallery scroller shares Heroes/Market grid sizing and the seven-column cap. A single 65% black SheetOverlay dims the live game; the drawer has no duplicate scenery, blur or sliding transform. A 140ms opening/100ms closing opacity fade respects reduced motion. Why: deployment retains immediate per-hero actions without moving or repainting a second full-screen world image.
- HUD content panels derive explicit viewport-bound width and height from the mine footprint in hud.css; content variants share viewport spacing and panel bodies own overflow. Why: switching Heroes and Mint cannot resize the frame or game, while Heroes responds to panel width.
- The live game and Test UI share GameHud and MineBoard presentation; mock sessions never supply real wallet credentials. Why: UI tests follow production HUD changes without invoking private game operations.
- Minting rolls independent rarity-bounded stats and derives level from their bonus-point sum; shared levelUpCost supplies both UI quotes and the wallet-validated server debit. Why: mint RNG stays consistent with the nine-point progression budget and quoted upgrade prices match charges.
- Xaman sign-in reports challenge-bound scan progress through the existing polling callback; signed, expired and rejected outcomes take precedence over opened metadata. Why: the dialog can acknowledge phone scans without weakening ownership verification or adding another connection.
- Dungeon movement, spawning and BFS targeting/escape share a per-tick bomb occupancy index, updated immediately on planting; only an already occupied origin can be exited. Why: all heroes see solid bombs without repeatedly scanning the bomb roster or replacing the existing pathfinder.
- Cancelling a dungeon target preserves an in-progress step; pathless fractional heroes recover along their occupied edge to a walkable endpoint before BFS replanning. Why: target destruction cannot strand heroes between tiles or let recovery bypass solid bombs.
- The public wiki owns a standalone reading layout in wiki.css, outside GameShell and GamePanel, with a sticky document header, chapter navigation and normal browser scrolling. It supports portrait reading without LandscapeGuard, uses browser-safe shared game constants and keeps chapter anchors within /wiki. Test UI's guide action navigates to /wiki rather than embedding it. Clearly separate available mechanics from unfinished payment/NFT features. Why: documentation reads independently of the game and stays aligned with playable rules.
- Partial chest HP persists only in private stage-map damage state via a session-guarded atomic wrapper with a last-sync compare-and-swap; lethal and partial reports share a server-team damage bound. Why: retries cannot heal chests, double spend time allowances, or write browser HP directly.
- Preserve the imported Chainframe TanStack Start application and its Phaser engine; Phaser loads dynamically to keep server rendering browser-safe.
- Keep this project's managed Cloud configuration and secrets separate from imported source; repository metadata and credentials must not overwrite project identity.
- Game tables and mutation RPCs are service-role-only with RLS denying direct browser access; existing server handlers validate hashed wallet sessions before accessing private state.
- Retain hero type and global mint numbers for sprite selection and identity tracking; display labels use the persisted name, with numbering kept separate.
- Share hero action controls between inventory and the game drawer; inventory persists through the existing wallet-validated state handler and updates the cached session, while the live drawer sends scene commands.
- Heroes and Test UI use shared HeroActionsPopover card controls, HeroFilters and MintHeroesContent; mint previews use an explicit mock adapter and bypass wallet reads and game-store writes. Why: collection space stays available while tests reuse production presentation without private operations.
- Shop is a shared navigation destination and owns MintHeroesContent; Heroes stays focused on the collection with no Mint button, and its empty state links to Shop. Test UI exposes the same Shop panel through an explicit mock mint adapter. Why: minting has one clear destination while previews avoid private operations.
- Shop uses hud-summoning rather than GamePanel: a full-width scene with actual rarity odds, a transparent gold/emerald gate centerpiece, and quantity/cost/summon controls beneath it (alongside it on short landscape screens). MintHeroesContent retains its wallet validation, mock adapter and reveal dialog. Why: summoning has a scene-led layout without inventing booster mechanics or changing the mint economy.
- Single-session lock: loading the game opens a game_sessions row (older ones close); save_progress requires the active session token and save_heroes_state rejects stale tokens, or token-less saves while a game was active in the last 2 minutes. Why: blocks multi-tab farming server-side.
- Phase 2 anti-cheat: hero energy saves are clamped server-side against the stored state (src/lib/game/heroes/energy.ts). There is no daily chest quota — stamina is the only earning limit. Why: client-reported energy and mining rate are untrusted.
- Phase 3 multi-tab notice: /play heartbeats checkGameSession every 15s (detects superseded sessions across devices, reports live miner count) plus a BroadcastChannel for instant same-browser eviction. Why: game_sessions stays service-role-only, so browser Realtime subscriptions are not used.
- Remixes start with empty migrations; rebuild the service-role-only schema as a fresh baseline from scripts/schema.sql. Why: a remix boots clean on its own database.
- Hero marketplace: heroes carry their own sale/hold state; a buyer's hold lasts 5 minutes and the hero moves only after the worker verifies the payment (settle_market_purchase). Why: wallet transfers are slow and must never pay for a hero someone else got.
- Player milestones (XP, level, gold claimed, total + per-rarity chests) live in public.player_milestones, updated only inside save_progress from server-map chest data; equipped cosmetics are template IDs on players validated against the level. Why: one atomic write, client can't spoof XP.
- Players are wallet-only: `username` is the sole display name (editable on Profile, unique case-insensitive); legacy `display_name`/`email`/`password_hash` columns are dropped (0005) and must not return. Referrals use `players.referral_code` (?ref= link, applied only at account creation via `referred_by`); the Referral window shows only the referred count. Why: one identity field, no email login.
- Hero economy: mint cost and energy settings come from constants/game.ts; max energy = stamina × ENERGY_PER_STAMINA, and natural rest is a flat ENERGY_RECOVERY_PER_HOUR for every rarity, shared by the client simulation and server clamp. Full natural rest hours = stamina × ENERGY_PER_STAMINA / ENERGY_RECOVERY_PER_HOUR; houses add bonus recovery on top. Why: one authoritative economy definition without assuming equal pool and recovery constants.
- Chest rarities use the hero rarity names (common, uncommon, rare, epic, legendary) everywhere: ChestRarity, chest textures, and player_milestones chests_* columns (renamed in 0006). Why: one rarity vocabulary across heroes and chests.
- Game pages render inside GameShell's viewport-height layout; the landing page and standalone /wiki own their layouts. Within GameShell only the middle viewport scrolls, fixed navigation stacks above content and below dialogs, and the decorative ledge is a separate world layer above the dimmer. Reserve control height rather than artwork height; /play renders directly into the viewport and other pages retain their content panel. Why: full-width artwork must not shrink content or move shared controls when scrolling.
- `.game-panel` in hud.css solely owns the panel frame (Phaser board styling); pages never style border/background on `.hud-content`. Why: one owner prevents drift.

- Fusion, Marketplace and Leaderboard are presentational components (FusionContent, MarketplaceContent, LeaderboardContent) fed by their routes or Test UI mocks. Fusion uses the open hud-fusion scene and collection wizard; Leaderboard uses the open hud-rankings ranked list; Marketplace shares Heroes' open collection layout, with buy actions in the card popover. HUD class names use the `hud-` prefix and landing classes `home-`; the old `v2` naming is retired. Why: Test UI reuses production presentation while each route retains its intended shell.

- Framed content pages use panel-page / panel-head / panel-scroll within GamePanel, with the shared stylesheet loaded by AppShell; gameplay, Heroes, Market, Shop, Fusion, Leaderboard and Profile remain unwrapped. Shared hud-collection rules own gallery scrolling and sticky controls. Why: headers stay stationary while content scrolls independently.
- The filter window is shared markup only: pages render `.fm-modal` / `.fm-*` (HeroFiltersDialog, MarketplaceContent) and its styling lives solely in src/styles/filter-modal.css, with the wooden 9-slice frame supplied by the shared popup rule in hud.css. Why: one filter design serves every panel, and a page stylesheet that redeclares it drifts.
- Heroes and Market use a full-width hud-collection instead of GamePanel in AppShell and Test UI, with one page scroller and transparent sticky controls aligned right, without a title, icon or count. The shared grid caps at seven columns, using 200px cards and 35px column gaps on desktop, 100px cards and 5px gaps below 768px. Sort by and Hero selectors apply inline; filter dialogs own rarity and minimum stats plus Market's price bounds, and clearing a dialog preserves the inline selectors. Market cards place coin prices and colored Yours/Held status in a dark gold-edged plaque aligned with the visible card frame; purchase actions remain in the card popover. Shop and Fusion use their own open scene shells. Why: both collections share the open gallery layout while preserving wallet-validated purchases.

- Leaderboard uses hud-rankings in routes and Test UI, with a fixed title/pager, one scrolling table and sticky column headings. paginateLeaderboard serves the complete snapshot in groups of 100 without a top-100 cutoff; Test UI has 250 entries using the same helper. Scoring, wallet validation and the service-role snapshot stay unchanged. Why: pages represent ranks 1–100, 101–200 and subsequent groups without rewards, season or My Rank sections.

- Profile uses hud-account-page with open identity/progress, flat milestone and rarity summaries, and HousePicker. All five houses are demo choices until NFTs launch. HouseRegistration refreshes the wallet-validated inventory, replaces only demo houses through existing unregister/register RPCs, reloads after success or failure and invalidates cached sessions; switching returns resting heroes to the roster. Test UI shares one demo tier and hero roster between Profile and House without private operations. Why: the selected demo is the house players actually open and use, without implying NFT ownership or minting.

- Profile cosmetics contain only avatars and backgrounds: visual slots 1–10 are heroes, 11–20 special cards, and 21–25 empty partnership reservations. Persisted avatar IDs remain 0–19 and backgrounds 200–219; reserved IDs and retired banners cannot equip. Avatars are 512×512 and backgrounds 1672×941 under public/assets; background 1 is the original valley. GameHud's --hud-background and header identity use authenticated equipped cosmetics, mirrored by shared local Test UI state. Keep the 70% scenery overlay independent of artwork. Why: changing appearance updates the whole game without reviving banner UI or implying partnership art is available.

- Avatar artwork is a purpose-drawn profile portrait set, with square shoulders, an upright front-facing head, direct eye contact and one consistent cheerful expression/framing. Use the approved Moss portrait as the pose/style master and the hero cards only for identity; never substitute crops or card action poses. Preserve masks/species features while matching the friendly eyes. The avatar catalog URL includes an art revision so replacement PNGs refresh in existing sessions.

- Wallet lives at /wallet inside the unframed hud-wallet-page shell. Header gold plus navigates to Deposit and account Withdraw navigates to the Withdraw tab. WalletContent shares presentation with Test UI, accepts read/withdraw adapters, validates whole-coin bounds and requires an explicit review before the existing wallet-validated atomic withdrawal handler. Deposit details only display configured treasury/tag data; history keeps pending separate from completed. Test UI uses mock balances and never submits private operations. Why: account actions have a dedicated page without invented conversion rates or payment completion.

- Serve verified WebP derivatives for static UI art, keeping PNG masters. npm run assets:optimize encodes and checks visible RGBA/alpha/dimensions, selects only smaller outputs, regenerates src/lib/assets/optimized-images.ts and rewires static URLs. All current groups use lossless WebP; dynamic cosmetics/stat/emblem paths use optimizedImage, preserving cache queries and PNG fallback. Keep SVG icons and Phaser source loaders unchanged. The measured sizes and per-file validation live in docs/webp-report.md.
